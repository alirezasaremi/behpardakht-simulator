# Callback

## Documented callback (`PROTOCOL`)

After banking operation, gateway POSTs following values to `callBackUrl` supplied with `bpPayRequest` (v1.39 printed page 33):

| Field | Source type | Source meaning |
| --- | --- | --- |
| `RefId` | `string` | Payment-request reference generated with Pay. |
| `ResCode` | `string` | Purchase status; response-code catalogue applies. |
| `SaleOrderId` | `long` | Purchase request number. |
| `SaleReferenceId` | `long` | Purchase transaction reference provided by bank. |
| `CardHolderPan` | `string` | First six and final four card digits. |
| `CreditCardSaleResponseDetail` | `string` | Credit-purchase response detail. |
| `FinalAmount` | `long` | Final cardholder-debited amount in online discount scheme. |

Before calling Verify, merchant must verify callback `RefId` and `SaleOrderId` exactly match `RefId` and original Pay `orderId` for same transaction. If mismatched, source requires merchant treat transaction invalid and not call `bpVerifyRequest`.

`callBackUrl` must be within merchant registered domain. Local simulator must additionally use an allowlist and SSRF protections; that is `SIMULATOR_INTERNAL`, not claimed source behavior.

## Goal 4 callback payload (`SIMULATOR_INTERNAL` unless marked)

Goal 4 uses source-exact field names and `POST`, but source does not specify encoding/content type. Local dispatcher therefore uses `application/x-www-form-urlencoded;charset=UTF-8`; this is not a production compatibility claim. `RefId` is stored Pay RefId. `SaleOrderId` is original Pay `orderId` (`PROTOCOL`: printed page 11 says Sale-stage `orderId` becomes `SaleOrderId`; printed page 33 requires callback value match Pay's sent `OrderId`). `SaleReferenceId` is injectable, unique-in-process, decimal `bigint` generated by simulator, not a provider algorithm. In the simulator, successful `FinalAmount` equals stored Pay amount; its single cancellation scenario uses `0`. This is a simulator decision, not discount-scheme behavior.

`CardHolderPan` is fixed `000000*****0000`, intentionally invalid/masked and never collected from a user. `CreditCardSaleResponseDetail` is empty because Goal 4 does not implement credit Iranian-goods purchase semantics. Both are simulator-only safe representations, not production values.

Success uses documented `ResCode` `0`. Goal 4's single non-success page action uses documented table-11 `17` (user/cardholder cancellation). Selecting it is `SIMULATOR_SCENARIO` simulator decision, not a claim about production UI/provider triggering or every unsuccessful payment.

## Callback dispatch security (`SIMULATOR_INTERNAL`)

`SIMULATOR_CALLBACK_ALLOWED_ORIGINS` is a comma-separated exact-origin allowlist. Empty or malformed configuration permits no callbacks; `localhost` and `127.0.0.1` require explicit origin entries (including port). Destination URLs must parse, use `http:`/`https:`, contain no username/password, and match an allowed origin. Dispatcher uses stored Pay `callBackUrl` only; browser actions cannot override it. It does not follow redirects, bounds request time to three seconds, and reads at most 16 KiB of response without storing body content.

It records safe dispatch attempted/succeeded/failed events with HTTP status where available. A non-2xx HTTP response, timeout, rejected destination, or transport failure remains callback transport state only; it never retroactively changes Sale, creates a Behpardakht ResCode, or retries. Each accepted local payment action makes one synchronous delivery attempt; duplicate payment actions reject and no delayed or duplicate-callback scenario exists. This deliberate local behavior is covered by payment and dispatcher tests, not claimed as Behpardakht behavior. Exact-origin checks do not prevent a trusted hostname from later resolving to a changed IP address; this residual DNS rebinding limitation remains documented.
